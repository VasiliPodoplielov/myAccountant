# CLAUDE.md

Загальні правила роботи з репозиторієм і кодом.

## Перевірки

npm workspaces (`apps/*`, `packages/*`), усі команди запускаються з кореня:

| Що | Команда |
|---|---|
| Typecheck | `npm run typecheck` |
| Lint | `npm run lint` |
| Формат | `npm run format:check` (виправити: `npm run format`) |
| Тести | `npm run test` |

«Прогнати перевірки» нижче означає всі чотири.

Тести `packages/firestore-rules` запускають емулятор Firestore: потрібна **JDK 21+** (`java -version`) і доступ до `firebase-tools`. На Windows, якщо емулятор падає з `Unable to establish loopback connection`, задайте `JAVA_TOOL_OPTIONS=-Djdk.net.unixdomain.tmpdir=C:\jtmp -Djava.io.tmpdir=C:\jtmp` (тека має існувати).

## Git

### Гілки

| Гілка | Що там | Як потрапляє |
|---|---|---|
| `main` | Production: лише завершені й перевірені зміни | PR з `dev`, мержить розробник |
| `dev` | Інтеграційна гілка | PR з робочих гілок, мержить розробник |
| `feature/<опис>`, `fix/<опис>`, `chore/<опис>` | Одна задача | Створюється від свіжого `dev` |

- Усі зміни потрапляють у `dev` і `main` лише через pull request. Ніколи не комітити й не пушити напряму в ці гілки.
- Ніколи не мержити PR самостійно: це робить розробник.
- Перед першою зміною коду перевірити поточну гілку. Якщо це `dev` або `main`, спершу створити робочу гілку.
- Нова гілка: `git fetch`, `git switch -c <гілка> --no-track origin/dev`, перший push — `git push -u origin <гілка>`.
- `<опис>` — короткий, латиницею, через дефіс: `feature/vat-report`.

### Коміт, push і PR

- `git commit` і `git push` — лише на пряму вимогу розробника («закоміть», «запуш»). Завершена задача чи успішні тести не є дозволом.
- «Закоміть» не означає «запуш»: кожна дія потребує окремої вимоги. PR створюється одразу після push без окремого прохання.
- Порядок: рев'ю → виправлення → коміт → push → PR.
- Перед комітом:
  1. `git fetch`, потім code review усіх змін гілки й робочого дерева: `git diff --merge-base origin/dev` плюс неотрековані файли (`git status --short`).
  2. Самостійно виправити всі знайдені баги, не чекаючи окремого прохання. Не виправляти лише те, що потребує рішення розробника: назвати це у звіті з причиною.
  3. Прогнати перевірки.
  4. Якщо виправлення зачепили більше ніж кілька рядків, повторити рев'ю.
- Якщо перевірка падає, не комітити: виправити або повідомити розробника. Не обходити хуки (`--no-verify`).
- Перед push: ще раз прогнати перевірки. Повторне рев'ю не потрібне, якщо після коміту код не змінювався.
- Після push: створити PR у `dev` (`gh pr create --base dev`). В описі — що зроблено і як перевірено.
- Реліз у production: PR з `dev` у `main`, лише на прохання розробника.
- Ніколи не комітити секрети (`.env`, ключі, service-account файли): див. `.gitignore`.
