# JDG Ledger — roadmap

Особистий веб-додаток для обліку JDG на podatku liniowym з VAT: фактури доходу і витрат, VAT, ZUS, składka zdrowotna, zaliczki PIT, пізніше автоматичний імпорт фактур з KSeF.

Один користувач (власник). Мова інтерфейсу: українська. Терміни податкової системи лишаються польськими (przychód, koszty, zaliczka, JPK_V7M тощо).

---

## Як працювати з цим файлом (для Claude Code)

- Роби **один етап за раз**. Наприкінці етапу перевір усі критерії готовності і зупинись, щоб власник перевірив.
- Уся податкова логіка живе в `packages/core` як чисті функції з тестами. UI і бекенд лише викликають її.
- Гроші рахуй у **грошах (цілі числа)**, не у float. Конвертуй у злоті лише при відображенні.
- Не вигадуй ставки й правила. Якщо правило з розділу «Доменні правила» неясне або здається застарілим, спитай власника.
- Ніколи не коміть секрети: сертифікат KSeF, ключ service account Firebase, `.env`.
- Ендпоінти і формат API KSeF 2.0 бери з актуальної офіційної документації, не з пам'яті.

## Доменні правила (джерело правди для `packages/core`)

Параметри року лежать у конфігу `taxConfig[year]`, а не в коді. Значення на 2026:

| Параметр | 2026 |
|---|---|
| База duży ZUS | 5 652,00 zł |
| Emerytalna / rentowa / wypadkowa | 19,52% / 8% / 1,67% |
| Chorobowa (добровільна; власник **не платить**) | 2,45% |
| Fundusz Pracy | 2,45% |
| Разом społeczne + FP без chorobowej | 1 788,29 zł/міс |
| Zdrowotna liniowy | 4,9% доходу |
| Мінімальна zdrowotna: січень / лютий–грудень | 314,96 / 432,54 zł |
| Ліміт відліку zdrowotnej | 14 100 zł/рік |
| PIT | 19% |

### Розрахунок за місяць M

1. **VAT**
   - należny = продаж × 23% + VAT з import usług;
   - naliczony = відлічуваний VAT з витрат;
   - суми округлюються до повних злотих (JPK);
   - якщо naliczony більший за należny, надвишка переноситься в M+1.
2. **Витрати за категоріями**
   - *Авто мішане*: 50% VAT до відліку; у koszty PIT іде 75% від (netto + невідлічений VAT).
   - *Import usług* (Claude, інші закордонні послуги в EUR): VAT 23% одночасно należny і naliczony, сальдо 0; 100% у koszty.
   - *Офіс / інше*: 100% VAT, 100% koszty.
3. **Курс EUR**: середній курс NBP (tabela A) з останнього робочого дня **перед** датою фактури. Курс можна перевизначити вручну.
4. **ZUS społeczne** відлічуються від доходу. FP рахується як koszt. Усі składki (społeczne, FP, zdrowotna) відлічуються в місяці **сплати**, а не в місяці, за який нараховані (рішення власника):
   - składki за M сплачуються в M+1 і зменшують дохід та zaliczkę місяця M+1;
   - у січні відлічуються składki за грудень попереднього року (суми з налаштувань);
   - składki за грудень поточного року переходять на наступний рік.
5. **Zdrowotna за M** = max(4,9% × дохід за M−1, мінімум). Дохід = przychód − koszty − społeczne, сплачені в тому місяці.
   - Дохід місяця рахується наростаючим підсумком з січня: (дохід з початку року) − (доходи, вже враховані за попередні місяці). Збитковий місяць дає 0, а збиток зменшує дохід наступних місяців. Збитки минулих років базу не зменшують.
   - Для січня береться дохід за грудень попереднього року з налаштувань (порахований так само).
6. **Zaliczka PIT наростаючим підсумком**:
   - podstawa = Σ(дохід з січня) − Σ(zdrowotna, сплачена з січня, у межах ліміту), округлена до злотих;
   - податок = round(podstawa × 19%);
   - zaliczka = max(0, податок − сплачені zaliczki).
7. **Терміни сплати**: ZUS, zdrowotna, PIT до 20-го числа M+1; VAT до 25-го M+1.

Тести мають покривати: суму ZUS 1 788,29; мінімальну zdrowotną в січні й лютому; перенесення надвишки VAT; ліміт 14 100; авто 50/75; конвертацію EUR; наростаючу zaliczkę з місяцями без доходу; відлік składek у місяці сплати (січень з грудневими, зсув M → M+1); zdrowotną після збиткових місяців.

## Модель даних Firestore

```
users/{uid}
  settings/{year}          # ставки року, chorobowe, дохід і składki за грудень попереднього року
  incomes/{id}             # date, netto(grosze), vatRate, source: manual|ksef, ksefNumber?
  costs/{id}               # date, name, sellerNip?, category, currency, amount, vatRate,
                           # rateOverride?, source: manual|ksef, ksefNumber?
  ksefInbox/{ksefNumber}   # сирі розібрані фактури з KSeF, status: new|accepted|ignored
  vendorRules/{nip}        # NIP → категорія за замовчуванням
  fxRates/{date}           # кеш курсів NBP
meta/allowlist             # email власника
```

Правила доступу: читати і писати `users/{uid}/**` може лише `request.auth.uid == uid` з email зі списку дозволених. `ksefInbox` пише тільки сервіс (admin SDK), користувач лише змінює `status`.

## Етапи

### Етап 0. Підготовка (робить власник)
- [ ] Репозиторій на GitHub, Pages з джерелом «GitHub Actions».
- [ ] Проєкт Firebase: увімкнути Google Auth і Firestore (регіон `europe-central2`).
- [ ] Додати `<user>.github.io` у Authorized domains.
- [ ] Web-config Firebase покласти в GitHub Secrets як `VITE_FIREBASE_*`.

### Етап 1. Каркас і деплой
- Монорепо (npm workspaces), Vite + React + TS + Mantine, HashRouter, ESLint, Prettier.
- Workflow `deploy.yml`: build → Pages. У Vite вказати `base` з назвою репозиторію.
- **Готово, коли:** порожня сторінка з AppShell відкривається на GitHub Pages.

**Стан:** код готовий і перевірений локально (`npm run lint`, `format:check`, `typecheck`, `test`, `build`; сторінка відкривається через `npm run dev`). `base` не вписаний у код: `deploy.yml` бере шлях репозиторію з `actions/configure-pages` і передає у Vite через `BASE_PATH`. Лишилося власнику: етап 0 (Pages), злиття в `main` через PR (процес описано в `CLAUDE.md`) і перевірка сторінки на GitHub Pages.

### Етап 2. Податковий рушій `packages/core`

**Вже є, не переписувати з нуля:**
- `packages/core/src/tax.ts`: `TAX_CONFIG[2026]`, `CATEGORY_RULES`, `calcYear()`, `zusForMonth()`, `costNetPln()`, `nbpRateFor()`, `dueDates()`. Усі суми в грошах.
- `packages/core/src/tax.test.ts`: 20 тестів Vitest, усі зелені.
- Початкова версія була звірена з калькулятором на claude.ai на річному сценарії (VAT, ZUS, zdrowotna і PIT збігалися до гроша). Після переходу на відлік składek у місяці сплати (правило 4) і на дохід для zdrowotnej наростаючим підсумком (правило 5) zdrowotna і zaliczki PIT з калькулятором **більше не збігаються**; VAT і суми ZUS збігаються далі.
- Пакет оформлено: `@jdg/core` у npm workspaces, `package.json`, `tsconfig.json`, експорт з `src/index.ts`; тести запускаються в CI (`deploy.yml`).

**Що лишилося зробити:**
- Клієнт NBP: завантаження `api.nbp.pl/api/exchangerates/rates/a/eur/{from}/{to}/?format=json` у мапу `date → mid` і кеш у Firestore `fxRates`. Пошук курсу вже робить `nbpRateFor(date, table)`.
- Маппінг категорій: `carMixed` = паливо/авто мішане, `importServices` = Claude та інші закордонні послуги, `office`, `other`.
- **Готово, коли:** `npm test` зелений у CI.

### Етап 3. Авторизація і дані
- Вхід через Google, allowlist, `firestore.rules`, тести правил на емуляторі.
- Хуки для читання і запису `incomes`, `costs`, `settings` через `onSnapshot`.
- **Готово, коли:** після входу дані зберігаються і видні на іншому пристрої; інший акаунт отримує відмову.

### Етап 4. Інтерфейс
- **Рік:** таблиця на 12 місяців (przychód, koszty, VAT, ZUS, zdrowotna, PIT, разом, на руки) і підсумок за рік.
- **Місяць:** фактура доходу, список витрат, розбивка «до сплати» з термінами, деталі наростаючої zaliczki.
- **Додати витрату:** форма, зручна на телефоні, зі швидкими кнопками «Паливо», «Claude (EUR)», «Офіс»; курс EUR підставляється автоматично.
- **Налаштування:** ставки року, дохід за грудень попереднього року, składki за грудень попереднього року, сплачені в січні (społeczne, FP, zdrowotna).
- Світла і темна тема; польський формат чисел.
- **Готово, коли:** витрату можна внести з телефона менш ніж за 20 секунд.

### Етап 4a. ZUS helper (DRA)
- Автоматичного подання немає: публічного API ZUS для приватної особи нема, вхід у PUE йде через Profil Zaufany/банк, а робот у браузері крихкий. Додаток лише готує дані, подає власник.
- Екран «ZUS за місяць»: суми з `packages/core` (społeczne, FP, zdrowotna) розкладені по полях ZUS DRA (і RCA, якщо потрібна), з кнопкою «копіювати» біля кожного поля та терміном подання (20-те число M+1).
- Генерація XML у форматі KEDU для імпорту в PUE ZUS або Płatnik. Генератор живе в `packages/core` з тестами.
- Перед реалізацією звірити з актуальною документацією ZUS: перелік документів, які власник подає щомісяця, поточний формат KEDU, чи потрібна RCA.
- Нагадування в Telegram про 20-те число (спільне з пунктом з розділу «Пізніше»).
- **Готово, коли:** згенерований XML успішно імпортується в PUE ZUS, а суми збігаються з розрахунком за місяць.

### Етап 5. Перенесення даних
- Екран «Імпорт JSON» (формат: `{income: {1..12: {net, date}}, costs: [...], settings}`). Такий JSON власник отримає з калькулятора на claude.ai.
- Експорт року в CSV і JSON для бухгалтера або бекапу.

### Етап 6. KSeF: сервіс синхронізації (`apps/ksef-sync`)
- Спершу працювати на **тестовому середовищі** KSeF, потім на продукційному.
- Автентифікація в KSeF 2.0 **сертифікатом KSeF** (токени перестають працювати після 31.12.2026). Сертифікат і ключ лежать лише на сервері, з правами `600`.
- Інкрементальний запит фактур:
  - де власник **покупець**: це витрати;
  - де власник **продавець**: це дохід.
  Останню дату синхронізації зберігати в Firestore.
- Завантаження XML, розбір FA(3) у `packages/core`: NIP і назва продавця, дата, netto і VAT за ставками, валюта, номер KSeF.
- Запис у `ksefInbox` з дедуплікацією за номером KSeF. Категорію підказувати з `vendorRules`.
- Запуск через systemd timer раз на день, логи в journald, при помилці сповіщення в Telegram.
- **Готово, коли:** тестова фактура з середовища KSeF з'являється в `ksefInbox` з правильними сумами.

### Етап 7. KSeF: вхідні в UI
- Екран «Нові з KSeF»: прийняти (стає `cost` або `income` з категорією), змінити категорію, ігнорувати.
- Опція «запам'ятати категорію для цього NIP» записує правило в `vendorRules`.
- Бейдж із кількістю нових фактур у навігації.

### Етап 8. IP Box (окремо, за бажанням)
- Позначати частку доходу як kwalifikowany IP, вести облік за місяцями, рахувати wskaźnik nexus.
- Річне порівняння 19% і 5% для сум, що відповідають умовам IP Box. Цим замінити окрему таблицю в Excel.
- Перед реалізацією узгодити з власником, як саме він зараз веде цю таблицю.

## Ризики й обмеження
- API KSeF 2.0 нове, деталі можуть змінюватися. Не прив'язуйся до нього жорстко і тримай KSeF у межах `apps/ksef-sync`.
- Закордонних фактур (наприклад, Claude) у KSeF немає. Їх завжди вносять вручну.
- Річне розрахування zdrowotnej, PIT-36L і JPK додаток не подає. Це довідковий інструмент, а не заміна бухгалтерії.
